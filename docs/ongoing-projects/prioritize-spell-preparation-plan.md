Let a Duris player type `prio full heal` to move every pending copy of Full Heal to the front of their preparation queue. A cleric with **bless → full heal → armor → full heal** queued would then pray for **full heal → full heal → bless → armor**. If Bless was already in progress, it stays queued and Full Heal starts on its own normal timer. If the first Full Heal was already in progress, it keeps its elapsed time.

## What the two reference games do

- **RealmsOfLuminari at `4f945b0`** registers a resting/sitting player command. Its live `do_prioritize` accepts a spell-name prefix, finds **all** copies on the pending list, removes them, and prepends replacements. Ready copies live in separate counters. During active study the command silently stops the event and restarts it for the new head. The stop also clears meditation, and naming a valid spell absent from the queue returns before the restart. The older handler under `#if 0` and the older news entry describe a previous restriction on active use. Adopt the live command’s all-copies behavior and avoid those interruption side effects. [Command and queue code](https://github.com/LuminariMUD/RealmsOfLuminari/blob/4f945b0e0c0485178d1dbf531d82db91ef1060be/src/memorize.c#L2059-L2241) · [Silent stop](https://github.com/LuminariMUD/RealmsOfLuminari/blob/4f945b0e0c0485178d1dbf531d82db91ef1060be/src/memorize.c#L781-L787) · [Registration](https://github.com/LuminariMUD/RealmsOfLuminari/blob/4f945b0e0c0485178d1dbf531d82db91ef1060be/src/interp.c#L2066) · [Player help](https://github.com/LuminariMUD/RealmsOfLuminari/blob/4f945b0e0c0485178d1dbf531d82db91ef1060be/lib/information/help_index#L9611-L9618)
- **Luminari-Source at `77d9b032d`** mentions `prioritize` in the design comment above `do_gen_preparation`. Its command table has no such verb. Its implemented preparation model distinguishes class-specific prepared-spell queues from innate slot recovery. Prepared entries carry a spell, metamagic, domain and preparation time. `prep_queue_add` inserts at the head, and the event decrements the head’s own time before moving it to the collection. The useful distinction for Duris is whether the player actually has *named* spells to reorder. ## Duris implementation

Duris already has the queue. `do_memorize` appends a `TAG_MEMORIZE` affect whose `modifier` is the spell ID. A clear `MEMTYPE_FULL` bit means pending. `use_spell` moves a spent, reusable copy to the tail. The pending section of `memorize`/`pray` walks this same list. `handle_memorize` completes the first pending copy it can study, skipping inaccessible books. The separate `memorize_last_spell` mechanic restores from the opposite end. These consumers should all see the new order through the list they already use. Baseline inspected at Duris `57a8ecbb7`, with preparation and persistence sources also checked against local `origin/master` at `aaba7088d`. [Memorization](../../src/classes/memorize.c) · [Affect list operations](../../src/magic/affects.c)

1. **Register the player command.** Append `CMD_PRIORITIZE` at the next available real command ID on the implementation branch. Append `"prioritize"` before the command table’s newline sentinel, increment `MAX_CMD`, and declare `do_prioritize` beside `do_forget`. Use `CMD_Y(CMD_PRIORITIZE, STAT_RESTING + POS_SITTING, do_prioritize, 0, FALSE)`, as for `memorize`. The normal prefix resolver supplies `prio` while existing abbreviations still resolve as before (`p` to `puke` and `pr` to `practice`). This minimum permits arranging the queue while standing. Only the existing resting/sitting or kneeling recovery path starts paused study. Give the command the same meditation and concealment exemptions as `memorize`. Route the book check through the existing item-movement command fence, and include the verb in the storage locker’s existing preparation restriction. [Interpreter](../../src/cmd/interp.c) · [Command IDs](../../src/cmd/interp.h) · [Command count](../../src/core/config.h) · [Handler declarations](../../src/core/prototypes.h) · [Locker room hook](../../src/item/storage_lockers.c)

2. **Validate before touching a link or an event.** Implement the handler in `src/classes/memorize.c` beside the other player commands. Require a PC using named preparation. Use `meming_class` or `praying_class` together with the existing `USES_MANA` and `uses_slot_recovery` exclusions. This covers shamans and secondary-class casters while respecting transformations, equipment such as necroplasm, and alternate recovery interfaces. Trim the whole argument, normalize case, and pass the unquoted name to `lookup_spell` as a single string. Preserve its existing spell prefixes and renamed-spell alias. Check the resolved ID before indexing `skills`. Require a pending copy and a circle the character can currently prepare. For book users, share the existing availability check in `handle_memorize`, including its Chaos and Arcane Rudiments exceptions and inventory, hand, belt and ground lookup. A missing book gets its own explanation. A blank argument gets usage, an unknown name gets a lookup error, and a ready-only or absent spell gets “You have no pending copy of that spell.” Each leaves preparation intact. [Spell lookup](../../src/net/sparser.c) · [Class and resource predicates](../../src/core/utils.h)

3. **Move the existing pending copies.** In one forward traversal, keep the insertion link immediately before the first *nonmatching pending* entry. Splice later matching pending nodes at that link, advancing the insertion link past each moved node. This preserves the order of matching copies, the order of all other nodes relative to each other, and each node’s address and payload. Ready copies and unrelated affects can be interleaved anywhere in the chain. If the matching copies already lead the pending queue, report “already first” and skip the write. On a real change, mark `PLAYER_COMPONENT_AFFECTS` dirty as `prepare_battle_spells` does. Report the canonical spell name and number of pending copies prioritized. The priority applies to this queue once. Future casts still append their spent copies normally. [Existing dirty-mark precedent](../../src/cmd/battleprep.c)

4. **Charge the correct preparation time.** Record the original first pending node before the splice. Treat named recovery as active when `AFF2_MEMORIZING` is set and `get_scheduled(ch, event_memorize)` returns a live event. Duris’s `event_memorize` carries an optional duration for the meditation check and chooses the spell at callback time. Reordering alone could let a high-circle spell finish on a nearly expired low-circle timer. Apply the following rules. [Timer and failure handling](../../src/classes/memorize.c) · [Character event cancellation](../../src/world/new_events.c)

   - **Paused queue.** Publish the new order. A later `memorize` or `pray` resumes it.
   - **Active, same first pending copy.** Move any later duplicates forward. Keep the exact event, due tick, meditation phase and progress.
   - **Active, different first pending copy.** Disarm only `event_memorize`. Calculate `time = get_circle_memtime(ch, circle)` once for the promoted spell and call `schedule_memorize(ch, time / 2, &time)` just as normal named preparation does. Tell the player that switching spells restarts preparation time. This rule also covers moving a spell ahead of an earlier pending entry whose book has become inaccessible. Keep `AFF_MEDITATE` and `AFF2_MEMORIZING` on a successful switch. On scheduling failure, the existing wrapper clears active state, stops meditation and explains how to retry. The reordered choices remain available to resume.

   Notify `gmcp_spell_preparation_changed(ch)` after a real reorder, using the notification already in `schedule_memorize` on the restart path. The existing `Char.SpellPreparation` stream carries state and estimated seconds. The existing text commands show individual names and order. [GMCP publisher](../../src/net/gmcp.c)

5. **Use the existing save format and help pipeline.** `capture_affects` walks the live list in order. The snapshot repository inserts the rows in that order, the loader reads `player_affects ORDER BY id`, and materialization reverse-iterates before prepending each affect. The regular MariaDB checkpoint therefore carries the new order for old and new characters. This needs no schema migration, priority field, or per-spell timer. Add a `Prioritize` help topic and cross-links from `Memorize`, `Pray` and `Forget`. Keep the maintained help sources in sync and add the command attribute entry. Show an example with duplicates and explain the active-switch cost.
